Why springs, hover, fluid hover and press-shrink are built the way they are; read before changing `packages/fluid-functionalism/src/lib/fluid-hover.ts`, `fluid-highlight.tsx`, `press.tsx` or a component's motion.

## Springs and exits

- Springs are gpuix's native `motion` springs, not tweens. `fast`, `moderate` and `slow` in `packages/fluid-functionalism/src/lib/theme.ts` carry the numbers of the source's `springs.ts`, and velocity is kept when the target changes mid-flight.
- Exits are tweens (60 ms / 120 ms), as in the source. A target says so itself with its own `exit.transition` (`exit={{ opacity: 0, scale: .3, transition: DOT_OUT }}`); do not pick a transition by reading `useIsPresent`. Checks sample the exit's real end, not a fixed wait.
- Snap, don't spring, on a reflow: when a row moved because the layout changed (a filter, a collapse) the highlight jumps, and only pointer movement glides. A zero-length tween does the snap.

## Hover and press

- `hover:` and `active:` on one element are `style.hover` / `style.active`; `group-hover` and `group-focus-within` are `groupHover` / `groupFocusWithin` with a named group. gpuix applies these natively with no JS round trip, so a child that only restyles from its parent's hover or focus-within gets no signal.
- A signal (`onMouseEnter` / `onMouseLeave`) is right in three cases: the lit element is not the one under the pointer (the table row lights the fluid hover's pick, which can be a body row while the pointer is over the header); the value is read in JS (choosing between colour branches); or a parent `has*` state would have to style its children, or `:has(.x)` is needed, which gpuix lacks.
- Press-shrink is one `PressFill`: an absolutely positioned quad 1 px outside the pressable at rest, whose four edges the press pulls in. The source's inset layer plus same-colour spread shadow is two primitives that antialias separately, which shows as a grey ring on every rounded corner and doubles up under a translucent fill. The label is a `position: relative` box after the fill, so it paints over it with no `zIndex`. Cost: edges land on whole device pixels, so the 1 px pull-in is one step where the source eases through partial coverage.

## Fluid hover

One highlight glides between rows. Rules in `packages/fluid-functionalism/src/lib/fluid-hover.ts` and `fluid-highlight.tsx`:

- `pickNearest` is the source's, verbatim, so a pointer in a gap, in padding or past the last row still resolves to a row and the highlight never blinks out.
- One highlight per list; the sidebar shares one across the menu and its sub-menu rows.
- Entering the container starts a session, and a new session remounts the highlight so it appears at its row instead of sliding in from the last session's place.
- The highlight is owned by fluid hover. A Base UI primitive's highlight is controlled from `hover.activeIndex`, and a keyboard move calls `releasePointer()` so the scroll it causes does not re-pick a row under a stationary pointer.
- **Rows are measured as integers** (`toOffsetPx` in `packages/fluid-functionalism/src/lib/offset.ts`, half up like Chrome), because the source's `offsetTop` / `offsetWidth` reads are integers and gpuix has no `offset*`. The same function serves `toOffsetRect` and `createMeasuredHeight`, so every collapse, the sidebar, ask-user-questions and the viewport height spring to a whole-pixel `offsetHeight`. At scale 2 the showcase's "Searching profiles" step lays out 60.5 px where Chrome reads 61; `check-thinking-steps` pins the 61. Do not remove the rounding as a workaround when testing a newer ghia: it moves the highlight off the source's integers.
- **Rows are read in the container's layout pixels.** The highlight moves by `x` / `y` from 0,0 with `width` / `height` as box properties. `getBoundingClientRect` is the transformed box and nothing re-measures when a scale settles, so a hover that lands while a select or dropdown is still scaling in leaves the highlight off its row by that scale. `toOffsetRect` divides a row's offset by its container's box over the container's observed layout size (`ResizeObserver` border box), and `pick` takes that size too. It is invisible at rest and wrong only mid-animation; `check-popups` hovers a row mid-entrance. Do not simplify the division away.
- **The container rect is read on every pick**, as in the source, with no cache. A cache measured within noise against a live read once the bounds read after a paint-only write ran no layout pass (gpuix #47, October 2026). If a future pin makes the read slow, the symptom is idle frame-callback time on pages that autoplay a cursor (changelog, fluid-hover), not sweep draw p95: a sweep-only benchmark misses it.
- **Reads batch before writes.** A bounds read after a write that dirties layout is a forced pass over the whole retained tree. gpuix delivers every `ResizeObserver` callback in one loop, so each list's callback only measures and queues its write on a module-level list that one microtask flushes inside `batch`; `pick` takes the container box it was handed. A caller that adds a read after a write inside an observer callback brings back one pass per list, and no single-list check shows it. `check-command-menu` budgets the layout passes of entering the Command Menu page, a page of many lists, and fails it.

## Animation loops

Spinner, shimmer, word cycle, carousel fill and scripted cursors run on gpuix native animation (motion values, `repeat`, CSS keyframes), which costs no JS per frame. Do not add an `onFrame` loop for something a motion value or keyframe can play; `apps/demo/src/lib/clock.ts` lists who still uses `onFrame` and why.

- Pick the animation kind by what the property is. SVG attributes animate through keyframes (the button spinner is the source's `spinner-move` / `spinner-dash` on a `pathLength` 100 path); stroke draw and retract go through `CheckMark` (`motion.path` on `pathLength`); the file-thumbnail spinner is a bordered ring turned by a 1 s `spin` keyframe; the thinking-indicator shimmer is per-letter colour keyframes (`background-position` is not animatable) and its glyph a `motion.path` morphing `d`.
- `animate()` on a motion value returns playback controls (`pause()`, `play()`, `speed`), which is how the source holds an animation. The carousel fill is one animation held and resumed, with `play.speed` carrying a `duration` that changes mid-slide. Its reset and play are one effect, because Solid does not order effects: a play that ran before the reset read the old fill and never started. `finished` resolves only when the animation finishes or `complete()`s, never on `stop()` or replacement, so a finished fill asks for the next slide exactly once.
- Cost model (measured October 2026 on the gpuix `poc` branch, `83bab5a7` to `a92b4f7f`; re-measure on the current pin): a draw is cheap only if gpuix patches the tick. A paint-only tick (colour, opacity, SVG stroke, and transforms `x` / `y` / `scale`) is patched as its own unit; a layout loop (`width`, `top`), a box-size spring, a JS commit and an on-screen `layout` box draw the whole frame, which at a few thousand nodes is several milliseconds per tick against 1-3 ms. Before blaming a page's CPU on its loop count, read `patched/s` and `why` in `pnpm footprint`: a page with a loop and `patched/s` 0 has a blocker, not a cost. Do not wrap a native loop in a positioned or translucent ancestor without reading them.
- The thinking-steps demo cards start when half is in view and pause below 10% keeping their elapsed time (`observeVisibleRatio` in `packages/fluid-functionalism/src/lib/cull.ts`), as the source does; starting on mount ran shimmers off-screen and idled the page near 70% CPU.
