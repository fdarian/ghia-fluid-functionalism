Culling, the page-switch and scroll-write decisions, and how to measure idle CPU, memory and frame time without fooling yourself; read before touching `packages/fluid-functionalism/src/lib/cull.ts`, a scroll write, or quoting a perf number.

Every figure below was measured in October 2026 on the gpuix fork's `poc` branch, at the commit named beside it. Costs depend on the renderer's retention, bounds-read and patching behaviour, so none has been re-measured on the current `@ghia/*` pin. Re-measure before leaning on one, and write the load average next to every figure you record: runs compare only at a similar load.

## Culling stays

`packages/fluid-functionalism/src/lib/cull.ts` hides a region while it is a quarter viewport (`OVERSCAN`) from the page scroller, and holds `onFrame` and timer loops still while hidden (`OnScreenContext`). The renderer lays out and paints content a scroller clips away (gpuix #46), so a page of many menus costs several times a short one.

- It hides with `contentVisibility: 'hidden'` and `containIntrinsicSize: 'auto none'`. gpuix remembers a laid-out size only for an element whose style says `auto` while it shows, so the visible style carries `auto none` too, on both axes (one value would also set the width). A hidden region keeps only that remembered size; a report from a target with no box yet (height 0) is ignored, since hiding it would collapse the region.
- The fallback if a pin makes a read of hidden content dear (the renderer builds a skipped subtree for any geometry read) is a `display: none` wrapper that pins the region's height.
- Culling versus none (`pnpm perf`, then headless `pnpm footprint` with the observer effect knocked out, two alternating pairs each, `b03d4e27` and `196d69ce`): off was worse on 9 pages and better on none. Showcase idle CPU 31-45% to 69-80%, input-message 1.3-3.3% to 51%, fluid-hover 16-37% to 40-55%, changelog 19-37% to 32-46%, and 4-9 MB more memory on card, surfaces, command-menu, changelog and showcase. Idle CPU and sweep draw p95 regress independently, so read both.
- `content-visibility` against the `display: none` wrapper (headless, load 1.4-4.3, `a92b4f7f`): entry to the Command Menu page 1 layout pass against 2, one-column home tiles at their final height after settle, page switches, idle CPU and footprint equal.
- Costs of culling: a culled region has no built bounds, so a scenario that scrolls toward an element calls `shot.reveal` first, and an "is it hidden" assert uses `getBuiltElementBounds` (`getElementBounds` forces a skipped subtree and answers either way; see `check-doc-sections`, `check-changelog-rail`). The first draw of a long page is still whole, because a region is culled only after its `IntersectionObserver` has reported against a first layout.
- The source site uses no `content-visibility`; this is a port-only mechanism.
- The changelog's Releases jump re-aims: it computes its target while the entries above hold a remembered size, they are laid out again as the smooth scroll passes them, and a taller one moves the month. `release-spy.ts` recomputes on each page scroll and scrolls again when the target moved more than 1 px, stopping within 1 px, at the page end, or when the user scrolls away; it runs only while a jump is in flight. In 5 headless runs a single scroll without it landed exactly on 35 of 38 jumps, and the first jump from the page top (3 of 38) stopped 244 px short on the wrong month, cause not isolated, so the re-aim stays. It approximates the source's single `scrollIntoView` (`drift/site.md`).

## Scroll writes and page switches

On gpuix a JS write or read that touches layout while a motion value runs is billed as layout passes, and no frame is presented while they run.

- Scroll writes are the source's plain `scroller.scrollTop = top` (`writeScroll` in `command-menu.tsx`, `navigate` in `app.tsx`). If a pin ever makes the setter read metrics back, a held ArrowDown cascades (40-100 passes per drain, nothing drawn meanwhile). One pass per write that follows a mutation remains: it walks the whole retained tree, about 2.9 ms on the Command Menu page.
- The command menu skips its first `snapScroll(0)` (the `previousKey === undefined` return in the `rowsKey` effect): a fresh list is already at 0, and the page mounts many menus, each paying a whole-page pass (mount JS median about 400 ms to about 41 ms). Nothing but `perf-page-switch`'s mount JS sees that cost; a returning mount-time write passes every check.
- The `change` handler writes the motion value's live value, not the event's payload: a payload queued before a snap (the wrap from the last row to the first) would write the old bottom position back.
- A page switch writes the page scroller to the top before the swap (the source gets this from every App Router navigation), or the new page's height clamps the old offset and it appears scrolled. The write throws if the scroller is not mounted instead of skipping the reset.
- The Changelog's release spy defers its first reading to a 0 ms timer: reading the scroller at mount laid out the whole page (about 70 ms) before the first draw, so the newest month stands in until the real reading.
- A first visit to a long page still builds, lays out and shapes every node inside one whole-page layout. That is a renderer question (mount a region culled before its first layout), not something the port avoids.

## Measuring

The obvious check passes in each case below; use the stated one.

- **Held-key cascade.** `check-command-menu` holds an arrow at macOS repeat timing (initial 15, repeat 2, 60 Hz) with the motion clock running, since every pass samples the spring at the wall clock and a paused clock hides a cascade. It bounds layout passes per drain at 1 (a count, so load cannot move it), replays the wrap with keys back to back and one draw part way, and covers key drains only.
- **Page entry.** Counted as layout passes in a window drawn like a real one (screen reader off, draws only on a simulated display-link wake), because the real window blocked 1-1.5 s on forced passes that a test window drawing on every event never separates. The check opens the site menu, filters to Command Menu, presses Enter and runs wakes until 30 in a row draw nothing; entry is at most 4 passes (measured 2), one ArrowDown at most 1, then 2 s of idle with no pass and no drawn frame.
- **Forced-read probe.** `check-command-menu` prints, without asserting, what one `getElementBounds` costs on the settled page: a layout write (a 1 px height toggle) and a paint-only write (a background toggle), 20 reps each. Compare passes per read first; milliseconds only at a similar load. The renderer has no per-pass timer, so time is `performance.now` on the JS side.
- **Page-switch hitch.** `bun apps/demo/scripts/perf-page-switch.tsx <slug> --visits 4` splits one sidebar click into mount JS, first draw and later frames. Run one process per slug for a cold first visit (slugs in one process share text-shape caches).
- **Frame time.** `pnpm perf` answers how long a frame takes under a pointer sweep, on the real window. It cannot say what a still page costs a laptop.
- **Idle CPU and memory.** `pnpm footprint` (`apps/demo/scripts/footprint.tsx`, one child per page in `footprint-child.tsx`; flags in the headers):
  - The child is compiled, not run from source, unless `--source`, because Bun's transpile of the app's TSX lands in the process's memory and CPU. A source row is never compared with a bundle row; the label records the mode.
  - Headless (test renderer, emulated 75 Hz display link) tracks the animated-versus-static split of the real window and is the only mode that says how a tick was drawn (`patched/s`, `full/s`, `why`) and splits native from JS time. It says nothing about what the window itself costs. `draw ms` covers whole-frame draws only, so it rises when patching replaces cheap whole frames; compare `all draw ms` across pins that patch differently. Quote headless for "which page, which loop" and `--window` for "what does the user's machine pay".
  - `--window` is valid only for a visible window. A covered window gets no display link, so the driver reads `GPUIX_PRESENT_LOG` and flags the row `occluded` (exit 1) instead of printing a low CPU. The window is 1280 wide (the Electron comparison's size; the site's layout drops its sidebar below 1280) while `apps/demo/src/lib/window-options.ts` holds the shipped window, which the child reuses so they cannot drift.
  - `--tour` visits every page through the app's own `navigate` and reads the footprint fresh at each stop. Leaving a page returns nothing to the OS and a forced GC does not lower it: after the tour the introduction sat at 192 MB against 67 MB fresh. That is a high-water mark of malloc, JS heap garbage and CoreText instances, not a leak; read the retained element count (returns to 744) to tell the two apart.
  - Every spawn has a 30 s limit and a timeout names the command and the page. A synchronous `/usr/bin/footprint` can hang and block the child's own deadline, so memory is the child's RSS; say which when quoting a figure.
  - The driver records `loadavg` and uptime in the JSON.
- **Input to an idle window.** `apps/demo/scripts/check-idle-input.tsx` is headless on the test renderer's `postNativeEvent` and `setFrameWakeCallback`; it guards the lag after Cmd-K into the Command Menu once a page had stopped ticking.
- **An inert style can still dirty layout.** A `border-color` transition on a collapsed-table part once rebuilt the table's layout subtrees on every frame (5120 builds over one hover glide on the Table page against 12 for the sidebar). `check-table` therefore requires zero layout nodes computed, created and removed over the glide, and separately that the fade is drawn (screenshot the rule frame by frame with the motion clock held, pixel values strictly between the end colours), since a silently dropped transition also builds nothing. Measure layout work and pixels together for any "declared but inert" transition.
